# Internationalization (i18n)

QuickDrop uses standard Spring Boot + Thymeleaf i18n:

- `MessageSource` message bundles (`messages*.properties`)
- Thymeleaf message expressions (`#{...}`)
- locale switching with `?lang=<code>`

## Files

- `src/main/resources/messages.properties` (English source of truth)
- `src/main/resources/messages_bg.properties`
- `src/main/resources/messages_de.properties`
- `src/main/resources/messages_es.properties`
- `src/main/resources/messages_fr.properties`
- `src/main/resources/messages_it.properties`
- `src/main/resources/messages_ja.properties`
- `src/main/resources/messages_zh.properties`

Optional helper tooling:

- `.github/scripts/check_i18n_keys.py` (key consistency checker)

## Conventions

- Use dotted keys grouped by domain/page, for example:
    - `nav.*`
    - `button.*`
    - `badge.*`
    - `form.*`
    - `pagination.*`
    - `validation.*`
    - `notification.*`
    - `page.upload.*`
    - `page.fileView.*`
    - `page.files.*`
    - `page.share.*`
    - `page.paste.*`
    - `page.pasteView.*`
    - `page.history.*`
    - `page.dashboard.*`
    - `page.settings.*`
    - `page.adminFiles.*`
    - `page.adminPastes.*`
    - `page.adminPasteHistory.*`
    - `page.adminShareLinks.*`
    - `page.adminActivity.*`
    - `page.welcome.*`
    - `page.error.*`
- Keep keys semantic, not sentence-based.
- Add new keys to English first, then translate.

## Key style guide

Use flat dotted keys with stable prefixes. Recommended families:

**Shared / reusable**
- `nav.*` — navigation links and labels
- `button.*` — action buttons used across pages
- `badge.*` — status chips (Permanent, Hidden, Folder, Paste, …)
- `form.*` — shared form field labels and placeholders
- `pagination.*` — pager labels
- `notification.*` — transient UI toasts and alerts
- `validation.*` — form validation messages

**Page-specific**
- `page.upload.*`
- `page.fileView.*`
- `page.files.*`
- `page.share.*`
- `page.paste.*`
- `page.pasteView.*`
- `page.history.*`
- `page.welcome.*`
- `page.error.*`

**Admin pages**
- `page.dashboard.*`
- `page.settings.*`
- `page.adminFiles.*`
- `page.adminPastes.*`
- `page.adminPasteHistory.*`
- `page.adminShareLinks.*`
- `page.adminActivity.*`

Rules:

1. Reuse keys only when semantics are exactly the same.
2. Avoid generic names like `label1` or `textA`.
3. Prefer placeholders over concatenation.
4. Do not include HTML markup in message values.
5. Keep English as canonical source.

Examples:

- Good: `page.upload.title`, `button.save`, `validation.email.invalid`
- Bad: `uploadTitleText`, `message_12`, `saveTextForBlueButton`

## Translator notes

- Add translator notes as comments directly above keys in `messages.properties`.
- Use notes when placeholders or split strings are involved.
- Example note style:
    - `# Translator note: {0} is the app name.`
    - `# Translator note: split around numeric day count in template.`

## Fallback behavior

- Default locale is English.
- If a key is missing in a locale file, Spring falls back to `messages.properties`.
- QuickDrop does not rely on the server system locale.
- For unfinished translations, prefer omitting a key (fallback) over leaving an empty value.

## Adding keys

1. Add the key to `messages.properties` first.
2. Add translated values in each `messages_<locale>.properties` file you can validate.
3. If a translation is not ready, omit the locale key (English fallback applies).
4. Keep keys in the proper prefix family (`nav.*`, `page.*`, `button.*`, etc.).

## Adding a new locale file

1. Create `src/main/resources/messages_<locale>.properties` (for example `messages_pt.properties`).
2. Start by copying keys from `messages.properties`.
3. Translate values and keep key names unchanged.
4. Verify UI manually with `?lang=<locale>` and run the key check script.

## QA guardrails

QuickDrop includes a lightweight i18n CI check:

- Workflow: `.github/workflows/i18n-key-diff.yml`
- Script: `.github/scripts/check_i18n_keys.py`
- Current mode: warn-only (non-blocking)

The script reports:

- keys missing in locale bundles
- extra keys not present in English baseline
- empty values in locale bundles

Run locally:

```powershell
python .github/scripts/check_i18n_keys.py
```

Optional strict mode (for maintainers/future enforcement):

```powershell
python .github/scripts/check_i18n_keys.py --strict
```

### Unused-key and hardcoded-text check (`check-i18n.js`)

A second, complementary checker lives at the repo root. It runs three audits:

**1. Orphaned keys** — keys in `messages.properties` referenced nowhere in templates,
JS, or Java source. The opposite direction from the cross-locale diff above (dead
keys, not missing ones). Faster for a quick local check since it only reads the
English baseline and the source tree, not every locale file.

**2. Enum label coverage** — labels resolved at render time from an enum constant
(`#{page.history.actionType.__${entry.eventType.name().toLowerCase()}__}`) are invisible
to the orphan check, which treats the whole prefix as "covered". This verifies that every
constant of the mapped enum has a key. Five `SHORTLINK_*` event types shipped without
labels exactly this way, rendering the raw key on the activity page. Add new dynamic
prefixes to `ENUM_PREFIX_MAP` in the script.

**3. Hardcoded text** (`--hardcoded`) — user-facing strings that have no message key
at all, so they can never be translated no matter how complete the bundles are. The
cross-locale checker cannot see these: a string that was never keyed simply isn't in
any bundle to be reported missing.

It walks templates with a tag stack, so a text node is attributed to its enclosing
element. That matters for mixed content — in
`<button><span aria-hidden="true">&#9656;</span> Technical info</button>` the label
belongs to the `<button>`, not the `<span>` beside it, and a naive
`<tag>text</tag>` match misses it entirely.

Skipped as legitimate, not gaps: elements whose text comes from
`th:text`/`th:utext`/`th:field`, language-switcher entries (a switcher shows each
language in its own language — "Deutsch" stays "Deutsch" in every locale), bare
entities and glyphs, pure numbers, and JS template literals that are mostly
interpolation. Comments are blanked before scanning so JSDoc usage examples don't
register as shipped copy.

```bash
node check-i18n.js               # orphaned keys
node check-i18n.js --hardcoded   # untranslatable strings
node check-i18n.js --all         # both
node check-i18n.js --verbose
```

All three audits should report zero, and the script exits non-zero if any finds
something. If you add a user-facing string, give it a key in all eight bundles; if you
remove the last use of a key, delete it from all eight.

- `?lang=en`
- `?lang=bg`
- `?lang=de`
- `?lang=es`
- `?lang=fr`
- `?lang=it`
- `?lang=ja`
- `?lang=zh`

Example:

- `/file/upload?lang=de`

## Contributor workflow

1. Add/adjust key in `messages.properties` first.
2. Add translations for the same key in locale files.
3. Keep changes scoped to one page/feature when possible.
4. In PR description, include screenshots for changed text-heavy pages.
5. If translation is uncertain, leave the locale key out (English fallback is preferred over incorrect copy).
6. Follow key prefixes from this guide so contributors can find keys quickly.
7. If you rename or delete keys, include migration notes in the PR.
8. Keep i18n PRs focused by page/feature to simplify review.

## Suggested review checklist

- Keys follow approved prefixes and naming style.
- English text is clear and context-accurate.
- Placeholder usage is correct (`{0}`, `{1}`, ...).
- No HTML is embedded in message values.
- Locale files are updated or fallback behavior is intentional.

## Notes on key ordering

- There is currently no auto-sort tool rewriting bundle files.
- Keep related keys grouped by section; avoid large unrelated reorder-only diffs.
